## 2. 原帖的核心主張

整份圖表的價值不在 100 項本身，而在它示範的下指令方式。原帖說得很直白：

- 含糊指令（「把程式碼弄乾淨」）對 AI 無效，因為它沒有指定要改什麼、改到什麼程度、改完怎麼驗。
- 有效指令是「診斷名 ＋ 技法名」：先說你看到的問題叫什麼（過長的函式、重複程式碼、看不出用途的名字），再說用哪個技法處理（抽取函式、合併、重新命名）。

這正是本庫 TECH-28《下 Prompt 的藝術》講的同一機制：規格與判斷標準要放在參考物與可量測的詞彙裡，而不是形容詞裡。這 100 招就是一份「重構詞彙表」，讓人和 agent 在同一組名詞下對話。圖表裡每一格都附一句可以直接送給 AI 的提示句，格式固定為「找出……，用……處理」，這是它與一般重構清單最大的不同。

## 4. 對照 Fowler 原典：這份清單是哪裡來的

Martin Fowler《Refactoring》（第二版 2018）是重構領域的原典，目錄分兩大部分：第三章的程式碼異味清單（診斷）與其後的重構技法目錄（操作，第二版共七十餘項，每項附操作步驟與範例）。

對照結果（我逐項比對）：

- 第一組 25 項異味，約二十項可以在 Fowler 的異味清單找到直接對應（過長的函式、重複程式碼、發散式變更、散彈式修改、特性依戀、資料群聚、基本型別偏執、重複的 switch、暫時欄位、訊息鏈、中間人、資料類別等）。第二版刪掉、第一版有的平行繼承階層與拒絕繼承也在這份清單出場；巢狀過深、義大利麵式程式碼、類別過度耦合是業界通用說法，不在 Fowler 的清單裡。
- 第二、三組的操作，大多是 Fowler 技法目錄的成員（抽取函式、內聯函式、移動函式、滑動陳述式、引入參數物件、移除旗標參數、封裝變數、上移方法、抽取父類別、攤平階層、用多型取代條件式、用管線取代迴圈、拆分迴圈、拆分階段、引入特殊案例、引入斷言、移除控制旗標等）。但第三組混入了幾項語言慣用語（可選鏈結、空值合併運算子、三元運算子、短路求值），這些是語法糖，不是 Fowler 意義下的重構技法。
- 第四組整組不是 Fowler 的技法目錄：原則部分（單一職責、DRY、KISS、YAGNI、關注點分離、迪米特法則、開放封閉）來自 SOLID 與軟體設計通識；安全程序部分（特徵測試、黃金樣本、絞殺榕、Mikado 方法）來自 Michael Feathers《Working Effectively with Legacy Code》與後續的遺留程式碼實務傳統，Fowler 本人也寫過絞殺榕模式的文章。量測部分（環狀複雜度出自 McCabe，認知複雜度出自 SonarSource 的規格）是工具時代的補充。

結論：這份清單是一份編得好的二次彙編，把七十年的重構正典壓成一面牆的詞彙。它的原創性不在內容，在包裝：每項都配好一句給 AI 的指令句，並且把「先具名、再動手」的用法寫進貼文。本文的證據等級據此定為：內容正典（可回原典查證）、編排與提示句為作者自製、未經第三方驗證。

## 5. 評估

### 5.1 值得收的三個理由

1. 詞彙即是介面。AI coding agent 缺的通常不是能力，是共同詞彙：同一個「把這個整理一下」，十次有十種改法。把 100 個名字固定下來，人指定方向、agent 執行、審查者用同一組名字讀 diff，三方成本都降。
2. 覆蓋面完整且誠實分層。診斷（第一組）、操作（二、三組）、安全（四組）的分層是真的分層，第四組的存在等於作者承認「會改」不等於「敢改」。這與本庫 ffmpeg-skill（TECH-21）的「先探測、再動手、必驗證」與 EGM（TECH-30）的把關設計是同一個信念的不同表面。
3. 被收藏的方式說明用途。3,260 收藏大於 2,121 喜歡，說明讀者把它當查表工具，不是當觀點文章。這正是入庫做索引的理由。

### 5.2 缺失與要注意的地方

1. 三種東西被壓成同一種單位。異味是診斷、技法是操作、原則是價值判斷，圖表都叫「招」。照著用沒問題，但教學上要講清三者的關係：異味指出病灶、技法是手術、原則是術後的生活方式，不能把原則當操作下令（「照 DRY 原則改」是含糊指令，違反這份圖表自己的主張）。
2. 方向相反的招式沒有標出取捨。圖表裡有好幾對互為反向的操作：#019 中間人（異味）同時有 #044 移除中間人與 #043 隱藏委派兩種反方向的解法，選哪邊取決於耦合的方向，圖表沒講；#026 抽取函式與 #031 內聯函式、#030 抽取類別與 #045 內聯類別也是成對反向。Fowler 原典對每一招都寫了動機與取捨，這份清單把那層去掉了。新手照表操課最容易在這裡翻車：招式名字對了，方向反了。
3. 沒有優先級。真實程式碼通常同時有十種異味，先改哪個（通常是先補測試、再處理重複與過長函式）圖表沒有給順序。本 dossier 第 6 節的使用協議補上這層。
4. 尤達寫法（#075）有爭議。多數現代風格指南不鼓勵把常數放左邊，而且現代編譯器與 linter 已經會擋下「把比較誤寫成指派」的錯誤，這一招在多數語言裡已經沒有實際保護作用，列在這裡比較像歷史遺跡。用不用隨團隊規範，不要當通則。
5. 給 AI 的提示句缺了一半。大多數提示句只說「改」，沒有說「改完跑測試」。第四組雖然有回歸測試（#078），但提示句本身沒有把驗證綁進每一次操作。用在 agent 身上時，要把驗證寫進指令模板，不然等於請 agent 開刀但不縫合。

## 6. 我們的使用協議（之後做優化時照這個用）

以下是我依這份清單與本庫既有紀律定出的調用方式，不是圖表原文。

1. 三段式，順序固定：診斷 → 單招操作 → 安全收尾。先用第一組的詞彙請 agent 盤點異味並編號回報，人（或主線）選要處理哪幾項，再逐項下令，最後照第四組收尾。
2. 一次一招。指令格式固定為：「編號與招式名 ＋ 範圍 ＋ 驗收條件」。例如「#026 抽取函式，只動 parseReport 內的日期處理段，行為不變，動手前先跑 #076 特徵測試鎖住現行輸出，改完跑 #078 回歸測試並附 diff 摘要」。禁止一次下十招，agent 的 diff 會大到沒人能審。
3. 沒有測試就沒有重構。目標程式碼若無測試覆蓋，第一步永遠是 #076 特徵測試（或 #099 黃金樣本），這是前置條件不是選項。呼應 TECH-21 ffmpeg-skill 的「未知不等於缺失、先探測再動手」。
4. 反向成對要寫明理由。用到 #043/#044、#026/#031、#030/#045 這類成對招式時，指令裡要寫為什麼選這個方向（耦合方向、呼叫頻率、變更熱點），審查者才有得對。
5. 跳過清單：#075 尤達寫法預設不用；第三組的語言慣用語（#063/#065/#066/#070）只在目標語言支援且團隊風格允許時用，並且不算「重構成果」單獨回報，它們只是寫法選擇。
6. 收尾清單：小步提交（#077）、回歸測試全綠（#078）、diff 由非製作者檢視（TECH-30 的金魚審查正好對位）、動到的地方順手整理（#084 童軍法則，只限本次動到的範圍，避免 scope 蔓延）。

## 7. 框架層（兩層寫法）

- 邏輯核心（動了就不是這個框架）：「行為不變」是重構的定義邊界，任何改變外部行為的動作都不叫重構，要另外走功能變更流程；以及「診斷、操作、安全」三段分工，三者不能混用（原則不能當指令、異味不能當成果）。
- 原情境表面（預期按個案換掉）：這 100 項的具體清單本身、日文／中文提示句的措辭、語言慣用語那幾項，以及尤達寫法這類時代性條目。換語言、換框架、換團隊規範時，清單內容可以增刪，核心不動。

## 第一部分 001–025 程式碼異味（診斷：看到訊號，先懷疑、再驗證，不要直接開刀）

### 001 過長的函式
- 背後邏輯：長度本身不是病，要同時記住的局部狀態太多才是。訊號是需要註解分段、捲動才看得完、看完記不住它到底做了幾件事。
- 注意點：長而平鋪的線性流程（依序驗證、依序組裝）反而好讀，硬拆只會製造跳躍式閱讀。
- 調用判斷：請 agent 回報行數加職責數，兩者都高才點 #026；驗新函式名能讓原函式讀起來像大綱。

### 002 重複程式碼
- 背後邏輯：同一條規則存兩份，遲早改一漏一，bug 以「另一處沒跟上」的形式出現。訊號是改一處時得先搜尋「還有哪裡也這樣寫」。
- 注意點：偶然相似不是重複，兩段今天一樣、明天會因不同原因分歧，硬併會綁死各自的演化。
- 調用判斷：先讓 agent 列出全部出現點與彼此差異，確認是同一條知識才合併；驗差異如何被參數化。

### 003 命名不清
- 背後邏輯：名字是零成本的文件，爛名字逼每個讀者重讀實作。最危險的不是沒資訊，是名字與內容不符，會主動誤導。
- 注意點：改名碰到公開 API、序列化欄位、資料庫欄位就不再是行為不變，要另外走相容性評估。
- 調用判斷：派工時給命名依據（領域詞彙），不要讓 agent 自由發揮；驗 diff 只有識別字變更、邏輯零變動。

### 004 巢狀過深
- 背後邏輯：每深一層，讀者腦中就多一個未結案的條件，堆疊超過三四層就開始讀錯。訊號是縮排深度和「這個 else 配哪個 if」要回頭找。
- 注意點：靠單一出口做資源清理、鎖釋放的程式，硬用提早返回拆巢狀會漏清理。
- 調用判斷：點 #051 守衛子句；驗每條提早返回路徑的清理與副作用完整，邊界測試覆蓋各層條件。

### 005 魔法數字
- 背後邏輯：裸數字沒有語義，讀者分不出 86400 是秒數還是巧合，日後也無法安全搜尋修改。訊號是數字直接參與運算或比較且換值就變質。
- 注意點：0、1 這類自明值不必命名；抽成常數但命名成 NUM_86400 等於沒抽，要用領域含義命名。
- 調用判斷：請 agent 列出全部候選與建議常數名供人審；驗常數值未變、所有引用點齊全。

### 006 過大的類別
- 背後邏輯：類別是概念的命名空間，什麼都往裡塞等於多個概念共用一個名字，改任何一處都要先理解全部。訊號是欄位與方法能明顯分成互不相干的幾群。
- 注意點：聚合根、框架控制器可能天然大，判準是「能否分群」，不是行數。
- 調用判斷：先交欄位分群分析，分得開才點 #030；驗拆分後公開介面不變或呼叫端同步更新。

### 007 過長的參數列表
- 背後邏輯：參數越多，呼叫端組裝成本與傳錯順序的風險越高，同型別連排尤其致命。訊號是呼叫時要對著宣告數位置、出現 null 占位與旗標。
- 注意點：先看參數是否同進同出（#014）；把無關參數打包只是把問題搬家。
- 調用判斷：點 #033 前先驗群聚證據；驗所有呼叫點編譯與測試通過。

### 008 無用程式碼
- 背後邏輯：死碼不是中性的，它謊報功能存在，吃掉編譯、搜尋與審查面積。訊號是無人呼叫的函式、永假分支、整段被註解掉的程式碼。
- 注意點：反射呼叫、框架回呼、公開 API 看起來沒人用其實是進入點，刪前要查動態引用。
- 調用判斷：要求 agent 附無引用證據（搜尋範圍與方法）；刻意保留的加註理由，不要留著裝沒事。

### 009 散彈式修改
- 背後邏輯：改一個概念要動很多檔案，代表這個概念沒有自己的家。訊號是同類需求的 diff 每次都散落十幾個不相關檔案。
- 注意點：日誌、權限這類跨切面關注點天然散佈，不在此列；病徵是業務概念散落，不是檔案數多。
- 調用判斷：先要變更熱點地圖，再用 #036/#038 收攏；驗同類變更日後只需動一處。

### 010 發散式變更
- 背後邏輯：與 #009 相反，一個類別因多種不相干的原因被改，表示它扛了多個變化軸。訊號看 git 歷史最準：同一檔案出現互不相關的 commit 主題。
- 注意點：拆分要沿變化軸切，不是沿長度切；用變更史判斷比讀程式碼更可靠。
- 調用判斷：請 agent 依 commit 歷史提出拆分軸；驗拆後每個類別的修改理由收斂成單一軸。

### 011 義大利麵式程式碼
- 背後邏輯：控制流靠旗標與遠端狀態交錯跳轉，局部推不出全局，任何修改都可能波及不可預測處。訊號是追一條流程要跨多函式反覆跳、狀態在遠處被改。
- 注意點：這是結構病，格式化治不了；順序必須是先鎖行為、再逐段理順，嚴禁整片重寫。
- 調用判斷：只准小步（#077），每次解一條流程線並附前後對照；驗特徵測試全程綠燈。

### 012 全域變數
- 背後邏輯：可變全域狀態沒有所有權，任何地方都能改，出事時追不到兇手。訊號是大家直接寫的靜態欄位與可變單例。
- 注意點：唯讀常數、不可變設定不在此列，病灶是「可變」加「無管制存取」。
- 調用判斷：點 #047 封裝收權；驗所有寫入收斂到單一入口，且該入口能加驗證或日誌。

### 013 特性依戀
- 背後邏輯：函式對別人的資料比對自己的還熟，代表行為放錯了位置。訊號是一個方法裡別人的 getter 連成串。
- 注意點：策略、訪客這類模式本來就設計成行為在外，那是刻意解耦，不是依戀。
- 調用判斷：點 #036 移動函式；只用到對方一小部分時，先抽出那一小段再搬，驗原類別介面沒有膨脹。

### 014 資料群聚
- 背後邏輯：起訖日期、經緯度這類值總是結伴出現，代表它們其實是一個未被命名的概念。訊號是同一組三四個參數在多個簽名重複。
- 注意點：只在單處出現、或不到三個值的偶然同行不要硬造物件，群聚要跨多處重複才成立。
- 調用判斷：列出群聚出現處證明至少數處後點 #033；驗新物件承接了驗證等行為，不只是資料袋。

### 015 過度依賴基本型別
- 背後邏輯：用字串裝 email、用整數裝金額，等於放棄型別系統幫你擋錯，驗證邏輯散落各處。訊號是同一欄位在多處被重複 parse 與檢查格式。
- 注意點：JSON、表單這類邊界層本來就是基本型別，值物件只做高風險概念，濫用會反噬。
- 調用判斷：先挑金額、識別碼動手；驗驗證收斂到建構子一處，非法值根本建立不出來。

### 016 重複的 switch
- 背後邏輯：同一組型別判斷散落多處，新增型別時必然漏改某處，而且靜默出錯。訊號是同一個欄位出現在多條 switch 或 if-else 鏈。
- 注意點：只出現一次的 switch 完全正常，病在「重複」；單處分支改多型是過度工程。
- 調用判斷：確認重複屬實後點 #054 多型或 #060 查找表；驗新增型別只需改一處。

### 017 暫時欄位
- 背後邏輯：欄位只在特定流程才有值，物件多數時間處於半合法狀態，讀者無從判斷何時能用它。訊號是大量 null 檢查與「只有 X 之後才有值」的註解。
- 注意點：快取、延遲載入的生命週期有明確管理，是正當用法；病徵是沒人說得清它何時有效。
- 調用判斷：點 #030 把欄位連同使用它的流程抽成專責物件；驗原類別不再出現該欄位的 null 守衛。

### 018 呼叫鏈過長
- 背後邏輯：a.b().c().d() 把呼叫端綁死在別人的內部結構上，中間任何一層改組都波及全部呼叫端。訊號是鏈上連續出現你不擁有的型別。
- 注意點：builder、查詢鏈這類流暢介面是刻意的鏈，不在此列；病徵是「穿透別人的內部」。
- 調用判斷：點 #043 在中間物件開一個有名字的方法；驗呼叫端不再引用深層型別。

### 019 中間人
- 背後邏輯：類別的方法大半只是一行轉呼叫，不提供語義只增加跳轉。訊號是打開類別，方法體清一色轉手、沒有附加判斷。
- 注意點：這是全表最需要分界的一項，轉呼叫若擋住結構變動或提供語義命名，就是 #043 要造的受控委派；純透傳才是病，解法是 #044。
- 調用判斷：請 agent 列出每個方法的轉呼叫比例與附加邏輯，全透傳才准移除，有語義的保留並標明理由。

### 020 過度泛化
- 背後邏輯：為「未來可能需要」預建的抽象與掛鉤，眼前只有維護成本，真需求來時形狀多半也猜錯。訊號是抽象類別只有一個子類別、參數永遠只傳同一種值。
- 注意點：公開 API 與協定的擴充點是契約不是泛化，刪前確認沒有外部實作者。
- 調用判斷：點 #045 或 #050 攤平；驗回報清單註明每個被拆擴充點原本預想的用途，之後要撿回來有據。

### 021 閒置類別
- 背後邏輯：職責少到不值得獨立存在的類別只增加導覽成本，跟只有一行的函式一樣該被併回去。訊號是方法寥寥且只是包住別人一層。
- 注意點：值物件、邊界標記這類小類別攜帶語義，小不等於閒置，判準是它有沒有自己的概念。
- 調用判斷：點 #045 內聯；驗併入後可讀性不降，語義性小類別保留並在回報說明。

### 022 資料類別
- 背後邏輯：類別只有欄位與存取器、行為全在別人手裡，等於把不變式開放給所有人隨意破壞。訊號是其他類別反覆拿它的欄位做同一套計算。
- 注意點：DTO、序列化模型、ORM 實體本來就該是純資料，不要對它們強加行為；病只針對領域物件裸奔。
- 調用判斷：用 #036 把反覆計算搬回資料類別；驗重複計算消失、不變式能在類別內部擋下。

### 023 平行繼承階層
- 背後邏輯：每加一個 A 子類別就被迫加一個 B 子類別，兩棵樹被隱形繩子綁住，代表有個維度放錯地方。訊號是類別成對命名、新增功能要同步開兩處。
- 注意點：有些雙塔是框架平台的要求，先分清耦合是自找的還是外部強加的。
- 調用判斷：請 agent 先畫成對對應表；通常解法是讓一邊引用另一邊取代平行繼承，驗新增一型只需開一處。

### 024 拒絕繼承
- 背後邏輯：子類別繼承了卻不用、甚至把父方法覆寫成空操作或丟例外，表示 is-a 關係不成立，繼承只是為了偷程式碼。訊號是呼叫前要先檢查型別才敢用。
- 注意點：也可能是介面切太粗造成的假象，先分清是繼承錯還是介面該拆。
- 調用判斷：改以委派取代繼承；驗子類別不再有禁用式覆寫，父類別出現處子類別都能替換（里氏替換成立）。

### 025 類別過度耦合
- 背後邏輯：兩類別互挖私有細節，彼此的實作就變成對方的既成事實，任何一方都動不了。訊號是雙向依賴、直接存取對方內部狀態。
- 注意點：同一聚合內的緊密協作正常；病徵是跨邊界、雙向、且挖的是細節而非介面。
- 調用判斷：請 agent 先列雙向存取點，再用 #036 移動行為或引入介面單向化；驗依賴方向變成單向。

## 第二部分 026–050 整理函式與類別（操作：每招都有反向招，方向先於動作）

### 026 抽取函式
- 背後邏輯：把有獨立意圖的一段程式碼命名，呼叫點讀得出「做什麼」、點進去才看「怎麼做」，同時得到可單獨測試的單位。
- 注意點：切口要沿語義邊界，不沿行數；若切出的函式要傳一堆參數又回傳多值，是切錯位置。名字想不出來，通常表示這段還不構成概念，先別抽。
- 調用判斷：派工註明抽取範圍與預期函式名；驗原函式讀起來像大綱、新函式參數數量合理。

### 027 重新命名變數
- 背後邏輯：變數名是作用域內最小的文件，data、tmp、flag 這類無資訊名逼每行都要額外解碼，名字與內容不符更會誤導。
- 注意點：作用域越大越值得好名字，只活兩行的迴圈變數不必大費周章；公開欄位改名先排除（相容性）。
- 調用判斷：低風險，可批量授權 agent 執行；驗 diff 純改名（靠重命名工具或全域搜尋佐證）。

### 028 修改函式宣告
- 背後邏輯：函式名與參數表就是契約，契約寫錯，全部呼叫端跟著誤解。訊號是名字要靠註解補充、參數順序反直覺、參數根本沒被用到。
- 注意點：公開 API 改宣告是破壞性變更，要走棄用流程（先加新、舊的標 deprecated），不能直接改。
- 調用判斷：派工要求回報全部呼叫點清單；碰到外部使用者就停下回報，不要默默改完。

### 029 抽取變數
- 背後邏輯：把複雜運算式的一段命名，讀者不必在腦中先算完才理解條件。訊號是 if 條件長到要逐段解析、正則或位元運算裸露在判斷裡。
- 注意點：同一運算式出現在多處時，抽變數只治局部，應該升級成 #026；變數名若只是運算式的複述，等於沒抽。
- 調用判斷：常與 #052 拆解條件式搭配；驗運算次數沒有因抽取增加，迴圈內不要重複求值。

### 030 抽取類別
- 背後邏輯：一個類別做兩件事，兩件事的變化理由與節奏不同，綁在一起讓每次變更都碰到全部程式碼。這是 #006 的處方。
- 注意點：抽完兩邊若仍頻繁互呼，只是把耦合搬到明面，分界可能劃錯，先看兩群欄位的交集大小。
- 調用判斷：分群分析先經人確認再動手；驗原公開行為不變、兩個新類別各自能獨立測試。

### 031 內聯函式
- 背後邏輯：#026 的反向。當函式體比名字更清楚、或只剩轉呼叫時，保留它只是多一層跳轉，展開反而直白。
- 注意點：多型方法、遞迴、公開 API 不能內聯；多處呼叫且函式體不短的，內聯會複製邏輯、製造 #002。
- 調用判斷：請 agent 列呼叫點數量，單點呼叫且體短才准；驗展開後沒有邏輯被複製擴散。

### 032 拆分變數
- 背後邏輯：一個變數先後扛兩種意義（先存輸入、後存結果），追值的人分不清它現在是誰，bug 常藏在第二次賦值。訊號是非累加地被賦值兩次以上且含義改變。
- 注意點：迴圈累加器是正當的多次賦值，病徵是「意義變了」不是「值變了」。
- 調用判斷：低風險，可直接授權；驗拆後每個變數只賦值一次（初始化除外），命名反映各自意義。

### 033 引入參數物件
- 背後邏輯：#007 與 #014 的處方。把結伴參數收成有名字的概念，簽名變短、呼叫端不再重複組裝、日後加欄位只改一處。
- 注意點：物件要順便承接行為（驗證、格式化）才有價值，純資料袋只是把長參數換個容器。
- 調用判斷：派工先交群聚證據（同組參數出現的函式清單）；驗呼叫端組裝程式碼確實變少、非法組合能在建構時被擋。

### 034 移除旗標參數
- 背後邏輯：布林參數讓呼叫點無法自解釋（doWork(true) 誰看得懂），且洩漏了「一個函式在做兩件事」。訊號是函式開頭就依旗標分兩大路。
- 注意點：拆成兩函式後內部若仍高度重複，要抽共用核心，不要複製兩份；旗標若是執行期才知道的狀態，未必拆得掉。
- 調用判斷：拆成兩個具名函式或改列舉參數；驗呼叫點讀得出意圖、差異部分清楚可辨。

### 035 分離查詢與更新
- 背後邏輯：方法既回傳值又改狀態，呼叫端就不敢重複呼叫、無法安心組合與測試。分開後查詢可隨意用、更新意圖明確（CQS 原則）。
- 注意點：pop、迭代器 next 這類「取即移除」是公認例外；外部不可見的快取懶載入也可視為查詢。
- 調用判斷：請 agent 標出所有「查詢帶副作用」的方法；驗查詢重複呼叫結果穩定、更新路徑能單獨測。

### 036 移動函式
- 背後邏輯：#013 的處方。函式該住在它最常對話的資料旁邊，位置對了，依戀與長呼叫鏈會一起消失。
- 注意點：搬移前先算它同時服務幾個主人；若兩邊都頻繁使用，搬去哪邊都只是換一邊依戀，可能要先抽取一小段，或留原處改傳參數。
- 調用判斷：派工附使用頻率表（存取兩邊成員各幾次）；驗原位置是否留轉呼叫殼要明說，避免留下 #019。

### 037 拆分處理階段
- 背後邏輯：一段程式碼前半在解析與準備輸入、後半在計算與執行，混寫讓兩段都無法單獨測試與替換。訊號是兩段之間存在一組明確的傳遞資料。
- 注意點：中間資料結構要正式定義，否則只是把一個函式切兩半，中間夾一個雜物袋參數。
- 調用判斷：先交中間表示的結構設計再拆；驗兩階段可各自單測、端到端行為不變。

### 038 將函式整合到類別
- 背後邏輯：#030 的反向。幾個函式反覆操作同一份資料、共享同一套前置處理，收進一個類別，共享狀態與不變式才有地方住（治 #022、#009 的一味處方）。
- 注意點：判準是有沒有共同的資料與生命週期，沒有就不要硬湊，湊出來就是下一個 #006。
- 調用判斷：請 agent 列出被整合函式共用的資料與前置步驟；驗呼叫端不再手動串接前置處理。

### 039 內聯變數
- 背後邏輯：#029 的反向。變數若只是運算式的別名、沒有增加資訊（算完存進 sum 再立刻 return sum），它只是噪音。
- 注意點：運算式昂貴或有副作用時內聯會重複求值；多處重用時內聯會製造重複。
- 調用判斷：小操作，隨其他重構順帶即可；驗被內聯處只有單次使用且運算無副作用。

### 040 替換演算法
- 背後邏輯：同一件事有更簡單的演算法或現成函式庫時，整段換掉比逐行修補更乾淨，手刻排序、日期運算這類已有標準解的最典型。
- 注意點：這是全組最容易改變行為的一招，邊界行為常藏在舊演算法的怪癖裡；沒有特徵測試覆蓋邊界，不准動。
- 調用判斷：硬性前置 #076 特徵測試或 #099 黃金樣本；驗新舊在測試語料輸出完全一致，效能宣稱要附量測。

### 041 移動陳述式
- 背後邏輯：相關的宣告與使用應該相鄰，眼球移動距離就是理解成本；宣告貼近使用處、相關段落併攏，也是為 #026 抽取鋪路的前置動作。
- 注意點：宣告之間若有相依或副作用，順序即行為，移動就不再是純整理。
- 調用判斷：通常作為前置步驟，不單獨回報成果；驗 diff 只動位置不動邏輯。

### 042 函式參數化
- 背後邏輯：幾個函式只差在某個固定值或一小段邏輯，把差異提成參數，就能消掉整群近乎複製的函式。
- 注意點：與 #034 不衝突，旗標參數的病是布林切開兩件不同的事，參數化處理的是同一件事的不同取值；合併後內部若長出大段依參數分支，是合錯了。
- 調用判斷：請 agent 列候選函式群與差異點；驗原函式行為逐一有測試對應、沒有長出新的旗標式分支。

### 043 隱藏委派
- 背後邏輯：#018 的處方。在中間物件開一個有名字的方法，呼叫端只依賴它的介面，背後鏈的結構就能自由改組。代價是中間物件會長出一排委派方法。
- 注意點：與 #044 的分界看兩件事，背後結構未來變動的可能性、委派方法有沒有語義；會變又帶語義就隱藏，純透傳就移除。
- 調用判斷：派工說明被隱藏的鏈與預期變動點；驗新方法都是語義命名，不是同名轉呼叫（那只是把 #019 做得更整齊）。

### 044 移除中間人
- 背後邏輯：#019 的處方。當中間層幾乎全是同名透傳，呼叫端直接找真正的物件反而更短，也少一處要同步維護的地方。
- 注意點：移除前查清這層有沒有在做存取控制、延遲載入、交易邊界或預留替換點，有任何一項，它就不是中間人而是邊界。
- 調用判斷：與 #019 共用診斷清單（透傳比例與附加邏輯）；驗被移除層確實沒有非透傳方法，呼叫端改向後測試全綠。

### 045 內聯類別
- 背後邏輯：#030 的反向。類別的職責被抽空、或從未長成時，併回使用它的類別，導覽回到一處。是 #020、#021 的共同處方。
- 注意點：若該類別承載刻意的值概念或邊界，內聯會抹掉命名價值，判準與 #021 相同。
- 調用判斷：驗併入後宿主沒有腫成 #006，公開介面的變化要在回報中列明。

### 046 工廠函式
- 背後邏輯：建構子名字固定、只能回傳該型別、表達不了建立意圖；工廠函式可以命名（createFromCsv）、集中預設值與建立邏輯，還能回傳子型別或既有實例。
- 注意點：語言若有具名參數或 builder 已足夠，工廠是多餘的一層；工廠若藏了讀全域設定、依環境切換這類智慧，建立行為會變得難測。
- 調用判斷：派工點名情境（多種建立來源、重複的預設組合）；驗建立邏輯集中一處、呼叫點讀得出意圖。

### 047 封裝變數
- 背後邏輯：#012 的第一步處方。把散落各處的直接讀寫收進受控的存取入口，日後要加驗證、日誌或換儲存方式，只改一處。
- 注意點：封裝只是收權不是治癒，存取器若是裸 getter/setter、運算仍散在外面，耦合原封不動；真正的目標是讓運算逐步搬回資料旁邊。
- 調用判斷：派工先盤點全部讀寫點；驗寫入收斂到單一入口且能加上不變式檢查（可配 #057 斷言）。

### 048 上移方法
- 背後邏輯：子類別有相同方法時上移到父類別，消除重複也消除漏改，概念上是把「共同」還給共同的家。
- 注意點：方法若只是長得像、實際依賴各自子類別的欄位，硬上移會拖出抽象方法群、甚至讓父類別反向依賴子類別細節；差異只在一個值時，改用 #042 或範本方法。
- 調用判斷：派工附各子類別版本的 diff 對照；驗上移後各子類別行為測試全綠、父類別不引用子類別專屬成員。

### 049 抽取父類別
- 背後邏輯：兩個無繼承關係的類別有相同行為與欄位，把共同部分抽成父類別，讓共同演化有一個家。
- 注意點：這是本段最容易做錯方向的一招。繼承是最強的耦合，「現在長得像」不等於「同一個概念」，兩者變化理由若不同，抽父類別等於把他們綁死，此時委派或共用函式更對。
- 調用判斷：派工先回答「這是同一個概念的兩種，還是兩個概念的巧合相似」，答不出來不准動。

### 050 攤平類別階層
- 背後邏輯：#020、#021 在階層上的版本。父子差異小到分層沒有回報時，合併成一個類別，省下導覽與理解的層數。
- 注意點：階層若對應公開 API 的型別契約或框架擴充點，攤平就是破壞性變更，先盤點有沒有外部子類別。
- 調用判斷：派工附父子差異清單，差異近乎為零才准點；驗合併後型別檢查與測試全綠。

### 051 守衛子句
- 邏輯：例外與錯誤路徑先攔截返回，主流程回到最左欄，讀者不必在腦中堆疊多層「如果」。
- 注意：守衛超過四五個，通常是函式在做太多事，不是排版問題；也別把真正的業務分支偽裝成守衛丟掉。
- 調用：巢狀深度 ≥3 且外層多為邊界檢查時點；驗主流程是否拉平、原有分支結果逐一不變。

### 052 拆解條件式
- 邏輯：條件難的不是布林運算，是不知道每個子條件代表什麼；抽成具名函式，條件式變成一句話。
- 注意：名字取錯比不拆更糟，會給出錯誤心智模型；拆出的須是純查詢，有副作用不能拆。
- 調用：條件逾三子句或多處重複時點；驗名稱與業務詞彙一致、能一口氣讀完。

### 053 合併條件式
- 邏輯：多個條件導向同一結果卻分開寫，讀者會以為它們有差別而逐一比對；合併是消除假差異。
- 注意：前提是後果完全相同且子條件無副作用；若只是目前結果相同、語義其實不同，合併會綁死未來的分化。
- 調用：連續 if 回傳同一值時點；合併後條件太長就先做 052 再合併。

### 054 多型
- 邏輯：依型別分支改為各型別自行實作，新增型別不必回頭改所有 switch，變更局部化。
- 注意：型別集合不穩定或行為只差一兩處時是過度設計；跨程序邊界的資料用不上。
- 調用：同組型別判斷重複三處以上（#016）時點；驗舊 switch 全數消失而非多包一層。

### 055 拆分迴圈
- 邏輯：一個迴圈同時算兩件事，兩件事被迫共用同一次遍歷的節奏與變數；拆開後各自命名、各自可測。
- 注意：代價是多遍歷一次，資料量大或遍歷本身昂貴（IO、查詢）時先量測再拆，不要為整齊犧牲效能。
- 調用：迴圈體內有兩段互不相干的處理時點；驗每個迴圈能否用一句話說完它在算什麼。

### 056 引入特殊案例
- 邏輯：null、空集合等特殊情況散落各呼叫端，總有人漏檢；收進特殊案例物件，呼叫端只管正常路徑。
- 注意：只適用能被「裝成正常」的情況；需呼叫端做不同決策的，硬裝會藏錯。
- 調用：同樣判空給預設值重複三處以上時點；驗呼叫端特殊檢查真的消失。

### 057 引入斷言
- 邏輯：把「這裡不可能發生」從心照不宣變成可執行檢查，錯誤在源頭爆炸，而不是在下游變成髒資料。
- 注意：斷言只用於程式員錯誤，不用於使用者輸入驗證；正式環境可能被關閉，不能拿它做流程控制。
- 調用：函式依賴未寫明的前提（參數非空、狀態已初始化）時點；驗違反前提時是否立刻、明確地失敗。

### 058 移除控制旗標
- 邏輯：旗標讓結束條件藏在狀態裡，要模擬整段才知何時停；改用 break、return，控制流直接可見。
- 注意：最易出錯的是「找到後要不要掃完」的語義差別，動手前先用特徵測試鎖住。
- 調用：迴圈出現 found、done 類布林且多處改寫時點；驗是否變成找到即離開。

### 059 集合處理管線
- 邏輯：map、filter、reduce 把走訪與計算分開，每步都是可命名的轉換，按管線順序就能讀懂。
- 注意：鏈太長、混入副作用或在熱路徑反覆配置會反噬；中間值看不見也是除錯成本。
- 調用：迴圈只做篩選、轉換、彙總且無中途 break 時點；驗結果與原迴圈逐筆相同。

### 060 查找表
- 邏輯：分支差異若只是輸入對應輸出，用資料表取代控制流，規則變成可增刪的資料。
- 注意：對應關係還會長出條件與例外時，表會被迫加欄位、變成另一種語言；缺值策略要先定。
- 調用：各分支只回傳不同常數或同構小計算時點；驗表完整覆蓋每個鍵。

### 061 策略模式
- 邏輯：把會變的算法抽成可替換物件，呼叫端依賴介面，新增算法不必改呼叫端。
- 注意：只有一種算法、看不到第二種時，是替想像的未來繳稅，與 YAGNI 衝突。
- 調用：同一計算已有兩種以上實作且依情境切換時點；驗切換點收斂一處、策略可獨立測。

### 062 快速失敗
- 邏輯：非法狀態越早被拒絕，錯誤位置離根因越近；在入口驗證，勝過在深處層層防禦猜測。
- 注意：這是對內部呼叫的紀律，對外輸入要轉成可理解的錯誤回應而非直接崩潰；入口驗過的也不要在深處重複驗。
- 調用：函式對參數做了假設卻不檢查時點；驗非法輸入是否第一時間以明確訊息被擋下。

### 063 三元運算子
- 邏輯：簡單二選一用運算式表達，不必為小分支拉出 if/else 與暫時變數。
- 注意：只適用選值不適用做事；巢狀或條件複雜時崩壞得比 if 更快。本庫列為寫法選擇，不算重構成果。
- 調用：單行、無副作用、兩結果都短時可用；讀著要停下來解析就退回 if。

### 064 德摩根定律
- 邏輯：人腦不擅長雙重否定，!(A 且 B) 與 !A 或 !B 等價但難度不同，變形是選更好讀的一面。
- 注意：只保證邏輯等價，不保證更好讀；有時保留原式或先替整體命名（052）才是解法。
- 調用：否定與 and/or 混排、讀者要停下驗算時點；先用真值表或測試確認等價。

### 065 可選鏈結
- 邏輯：?. 把逐層判空壓成一條鏈，消掉的是樣板不是判斷，取深層值的意圖露出來。
- 注意：它會把「中間層不該為空」的錯誤靜默成 undefined，下游更難查；鏈太長多半是結構異味，別用語法糖蓋。
- 調用：判空純為防禦樣板、空值語義就是「沒有」時點；驗被吞的空值哪些可接受。

### 066 空值合併運算子
- 邏輯：?? 只在 null/undefined 時給預設值，不像 || 會把 0、空字串等合法 falsy 值誤殺。
- 注意：0、"" 是合法值用 ??，代表未設定才用 ||；選錯是靜默的資料錯誤。
- 調用：|| 給預設值且左值可能合法為 0/"" 時點；逐欄確認 falsy 語義。

### 067 列舉型別
- 邏輯：狀態從自由字串收進有限集合，拼錯從執行期靜默錯誤變成編譯期錯誤，狀態空間可窮舉。
- 注意：適用封閉集合；值來自外部系統或持續增長的分類硬塞列舉，每次新增都要改版。
- 調用：同組狀態字串多處以字面值比較時點；驗字面值清零、switch 可窮舉檢查。

### 068 狀態模式
- 邏輯：行為隨狀態大幅切換且轉換有規則時，各狀態行為收進各自類別，消掉散落的狀態判斷。
- 注意：狀態少、差異小時是殺雞用牛刀，轉換表（073）或簡單 switch 更誠實。
- 調用：同一 switch(state) 在多個方法重複時點；驗新增狀態要動的檔案是否收斂。

### 069 模式比對
- 邏輯：把檢查型別、拆解結構、取出欄位合成一個宣告，分支條件直接長成資料的形狀。
- 注意：依賴語言與環境支援度，老環境硬用函式庫模擬更難讀；分支順序本身有語義，不要重排。
- 調用：連續 typeof/instanceof 加轉型取值時點；驗各分支變數綁定與原邏輯對應。

### 070 短路求值
- 邏輯：and/or 在結果已確定時跳過後續運算，既是效能也是語義工具：左邊成立，才有資格問右邊。
- 注意：把有副作用的呼叫放進短路鏈，等於讓副作用的發生取決於條件，讀者極易漏看。
- 調用：條件有先後依賴（先判空再取值）時用它排順序；驗每個子條件是否純粹無副作用。

### 071 吞掉例外
- 邏輯：本項是反面教材：空的 catch 把錯誤連同根因一起銷毀，系統會在別處以更詭異的方式壞掉。
- 注意：不處理也要留痕；記錄後照走只適用可降級的操作，核心流程吞了日誌還是錯。
- 調用：盤點所有空 catch 逐一裁決；驗每處例外都有去向：重試、降級、上報，三選一。

### 072 移出迴圈不變程式碼
- 邏輯：迴圈內每圈結果相同的運算重算 N 次是純浪費；移出還順帶宣告了「這件事與迭代無關」。
- 注意：前提是真的不變且無副作用；被移出的值若每圈其實被悄悄改動，移出就改變行為，先確認再動。
- 調用：迴圈體內有與迴圈變數無關的查詢、建物件或計算時點；驗效能差異是否值得，別為微優化破壞結構。

### 073 狀態機
- 邏輯：合法狀態與轉換寫成定義，非法轉換在結構上不存在，比事後加檢查更早排除整類錯誤。
- 注意：它管轉換紀律，不自動產生業務規則；狀態少時 enum 加 switch 就夠，上框架增成本。
- 調用：狀態以旗標組合或散落 if 表達、已出非法組合 bug 時點；驗轉換表窮舉、各轉換有測試。

### 074 決策表
- 邏輯：多條件決定結果時，人腦逐條讀 if 會漏組合；攤成表後，缺的組合與互相矛盾的列直接可見。
- 注意：表是檢核與溝通工具，不一定要變成程式碼；條件之間若有先後依賴而非獨立維度，硬攤表會生出假組合。
- 調用：三個以上條件交互決定結果、且曾因漏組合出錯時點；驗所有組合是否逐格有主。

### 075 尤達寫法
- 邏輯：當年防把 == 手誤成 =：常數放左邊，誤寫指派會因常數不可指派被編譯器擋下，是拿可讀性換保險。
- 注意：如今多半不需要：此誤寫多被編譯器或 linter 擋下，嚴格型別語言更寫不出來；留著只剩彆扭，本庫預設不用。
- 調用：不主動點；僅維護老 C 風格碼且團隊規範如此時隨現況。

### 076 特徵測試
- 邏輯：遺留程式碼沒有規格，現行行為（包括 bug）就是規格；先把輸出釘住，「行為不變」才有判準可驗。
- 注意：釘住的是現行行為、不是正確行為；發現疑似 bug 要記錄另案處理，不要在重構裡順手修。
- 調用：排在任何重構動工之前，是流程第一步不是選項；驗測試能否在未修改的程式上全綠。

### 077 小步修改
- 邏輯：每步小到可驗證，出問題時嫌疑範圍只有這一步；大步修改會把除錯變成考古。
- 注意：小步不等於慢，關鍵是每步結束時系統可編譯、可測試；半成品攤著不收尾才是真正的慢。
- 調用：派工時寫明每步的提交單位；驗提交紀錄是否一步一義、每步測試皆綠。

### 078 回歸測試
- 邏輯：重構的定義是行為不變，沒有自動回歸就只有信心沒有證據；它把「沒弄壞」變成可檢查的事實。
- 注意：全綠只證明被測到的沒變，覆蓋不足時是假安心；套件太慢會被跳過，先顧速度才有紀律。
- 調用：綁進每次操作收尾，模板固定寫「改完跑回歸並回報結果」；驗報告本體，不接受口頭保證。

### 079 單一職責原則
- 邏輯：一個元件只為一個變更理由存在，需求變動時爆炸半徑被限制在一個地方，負責人也明確。
- 注意：「一件事」沒有客觀粒度線，拆過頭會生出滿地小類別與跳來跳去的呼叫；判準是變更理由，不是行數。
- 調用：元件反覆因兩種不同需求被修改（異味 #010）時點；驗修改歷史是否收斂到單一主題。

### 080 DRY 原則
- 邏輯：同一條知識有兩個出處，改規則必漏改其一；DRY 消除的是知識重複，不是長得像的程式碼。
- 注意：把偶然相似、實屬不同概念的程式碼硬抽共用，之後兩邊互相遷就，就是錯誤抽象，代價比重複更高。
- 調用：同規則多處各自實作時點；判準是「改一個理由是否必然改另一個」；驗共用函式無模式旗標。

### 081 KISS 原則
- 邏輯：複雜度是未來每次修改都要付的利息；能直白寫完的，不先引入模式與間接層。
- 注意：刪的是不必要的複雜，不是必要的嚴謹（驗證、錯誤處理不能刪）；拿它當不補測試的藉口是反著用。
- 調用：審查時問「這層間接解決了什麼」，答不出來就移除；驗移除後行為不變、可讀性不降。

### 082 YAGNI
- 邏輯：替想像需求預建的機制多半永遠用不到，卻從第一天收維護費；需求出現再長，成本通常更低。
- 注意：資料欄位、公開 API 等日後難改的介面可先想一步，內部實作不行；那是分界線，不是擴充點。
- 調用：盤點出 #020 過度泛化時點名清除；驗被刪機制無現行呼叫者，無就刪。

### 083 關注點分離
- 邏輯：介面、邏輯、存取混在一起，動任何一層都要讀懂全部；分離讓每層可獨立理解與替換。
- 注意：分離為降耦合，不是比層數；小程式硬切五層、每層只剩轉呼叫，分離變繞路。
- 調用：同檔案同時有畫面字串、業務計算與 SQL 時點；驗改版面不碰計算、換儲存不動業務。

### 084 童軍法則
- 邏輯：腐化是每次「只求能動」累積的；經過的人留得比來時乾淨一點，改善才追得上腐化。
- 注意：只限本次動到的範圍，順手大掃除會讓 diff 失焦、審查失效；本庫協議已明訂。
- 調用：排進每次修改收尾，限動過的函式與檔案；驗順手改善與主任務可分辨。

### 085 單元測試
- 邏輯：把行為驗證縮到最小單位，失敗時定位精確，也逼設計長出可獨立呼叫的邊界。
- 注意：單元測試驗的是邏輯，不是系統接線；全是單元測試一樣會漏整合錯誤，比例要搭配整合測試看。
- 調用：重構中抽出的純函式與新邏輯優先補；驗測試是否只依賴該單位、失敗訊息能否直接指出哪條規則壞了。

### 086 Linter
- 邏輯：機械性的錯誤與風格問題交給工具即時擋下，人的審查精力留給邏輯與設計。
- 注意：規則要團隊共識後固化；警告太多會被集體忽略（警告疲勞），等於沒有；自動修復前先確認不會改到語義。
- 調用：專案層級常設；派工前確認 agent 產出有過 linter，驗零未處理警告。

### 087 程式碼格式化工具
- 邏輯：排版爭論沒有產值，交給工具一次定死，diff 從此只呈現真正的邏輯變化。
- 注意：第一次全庫格式化會產生巨型 diff，要獨立成一次提交，不可混進功能或重構的提交裡污染歷史。
- 調用：專案常設；驗 CI 是否直接擋下未格式化的提交，而不是靠人提醒。

### 088 環狀複雜度
- 邏輯：McCabe 數的是獨立路徑數，即測遍一個函式最少需要的案例數，是測試負擔與出錯密度的代理指標。
- 注意：只數分支不問難懂，一串簡單 case 也高分；當唯一門檻逼出把邏輯藏進資料表的假優化。
- 調用：設門檻（如 10 或 15）作警戒，超標先人工判讀再決定；驗超標清單與處置紀錄。

### 089 認知複雜度
- 邏輯：認知複雜度懲罰巢狀與跳躍式控制流，量的是「讀一段程式要花多少腦力」；088 量的是路徑數，兩者不同維度。
- 注意：低分不等於邏輯簡單，或只是把困難藏到別處；路徑多但平鋪與路徑少但深巢是兩種病，須並看。
- 調用：與 088 並列設門檻，先判超標屬哪一種；驗巢狀深度與中斷點實際下降。

### 090 程式碼覆蓋率
- 邏輯：它指出測試從未執行過的程式碼，那是行為完全未知的區域，重構從那裡開始最危險。
- 注意：覆蓋到不等於驗證到，無斷言的測試跑過也算；追 100% 會生出湊數測試。它是找盲區用，不是績效。
- 調用：重構前看目標模組覆蓋地圖，低覆蓋先補 076；驗錯誤處理、邊界值有被執行到。

### 091 型別註記
- 邏輯：把「這裡應該是什麼型別」從口頭約定寫進程式碼，錯誤在編譯或檢查期現形，agent 與人都少猜一層。
- 注意：註記要漸進且誠實，用 any 或亂標等於假型別，比沒有更誤導；先覆蓋邊界（API、共用函式）再往內。
- 調用：動態語言專案裡跨模組共用的函式優先點；驗型別檢查工具零錯誤通過。

### 092 迪米特法則
- 邏輯：只跟直接認識的物件說話；呼叫鏈每多一層，就多綁一層別人的內部結構，改版連鎖放大。
- 注意：管的是結構耦合不是呼叫次數；為遵守而到處加轉發方法，會長出 #019 中間人，兩方向一起判讀。
- 調用：出現 a.b().c().d() 火車殘骸時點（#018）；驗呼叫端依賴的型別數下降。

### 093 相依性注入
- 邏輯：把「用哪個實作」的決定從使用處抽走，測試才能換假實作，驗證不必連外部世界一起跑。
- 注意：為可替換與可測，不是每樣東西都做成介面；建構子參數爆炸時，先懷疑職責沒拆好。
- 調用：函式內部自己 new 外部服務或讀全域狀態時點；驗該單位不連網、不連庫可測。

### 094 純函式
- 邏輯：輸出只由輸入決定，行為可重現、可快取、可平行，測試不必先佈置世界狀態。
- 注意：系統不可能全純，目標是純邏輯最大化、副作用集中邊界；為純而把狀態傳到難讀就過了。
- 調用：計算與 IO 混雜時點名分離；驗同輸入重跑恆定、測試不需 mock 時間與亂數。

### 095 不可變資料
- 邏輯：資料不就地改寫，「誰在何時改了它」這個最難查的問題直接不存在，變化全走新值與明確路徑。
- 注意：深層全量複製有成本，熱路徑與大資料要量測；淺層凍結、內層仍可改，是假不可變。
- 調用：同物件被多處輪流改寫、bug 來自意外共用參照時點；驗改值都經產生新值的單一路徑。

### 096 絞殺榕模式
- 邏輯：新舊並行、流量逐步搬移，取代過程隨時可停可退，避免一次切換的大爆炸。
- 注意：前提是邊界可攔截（facade 或路由層能切流量）；並行是雙倍維護，先定退場條件與期限，否則舊系統死不了。
- 調用：排進大型取代專案，寫明各階段搬移比例與回滾方式；驗舊路徑呼叫量依計畫歸零。

### 097 命名規則
- 邏輯：命名一致，讀者能用模式掃描而非逐字解析，偏離慣例處自動跳出，提示有別的意思。
- 注意：規則管形式不管內容，合規但詞彙空洞（data、info、manager）照樣無資訊量；詞彙表另行維護。
- 調用：專案常設並寫進 linter；驗新碼零例外，舊碼被動到時逐步歸隊（配合 084）。

### 098 Mikado 方法
- 邏輯：先試做目標改動，讓編譯與測試逼出前置條件、記成相依圖，再按圖施工；未知變成可見清單。
- 注意：圖是工作文件，做完要收掉；圖太大通常代表目標切太大，先縮目標再畫。
- 調用：排在大型重構動工前做一次探索；驗前置任務全解、主改動落地無新驚訝。

### 099 黃金樣本測試
- 邏輯：輸出龐大、難逐項斷言的系統（報表、產生器），存一份經審核的完整輸出為基準逐字比對，漂移即現形。
- 注意：只知變了不知變對了，基準更新須人審，否則新 bug 被認證成新基準；含時間、亂數者先正規化，否則永遠紅燈被忽略。
- 調用：排在無一般測試的產生型系統動工前；驗差異逐項有人裁決。

### 100 開放封閉原則
- 邏輯：新增行為走新增程式碼而非改既有程式碼，既有行為不被新需求波及，舊測試續有效。
- 注意：需預判變動軸，猜錯軸時抽象層反擋路；同軸已出現兩三次變動，才值得開擴充點，是與 YAGNI 的平衡。
- 調用：同功能第三次以「再加一個分支」擴充時點；驗下次同軸新增只加新檔、不動舊檔。
